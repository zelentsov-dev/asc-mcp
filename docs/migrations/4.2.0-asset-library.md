# Migrating to the 4.2.0 candidate

The library version 4.2.0 targets selected App Store Connect API 4.5.1 changes. It does not implement every Apple operation. Candidate acceptance and stable publication are separate gates; installation examples in README remain on the previous stable version until publication.

## Existing integrations

All 502 existing tool names and 35 worker filters remain available. Their old call forms do not gain required arguments. `screenshots_*` continues to use screenshot, preview and set IDs. Those IDs are never translated into Asset Library IDs. Apple deprecated the legacy media resources in 4.5.1; compatibility remains subject to Apple's continued endpoint availability and real-API acceptance.

Apple now requires a plan-type filter when reading adjusted subscription equalizations. Existing calls to `subscriptions_list_price_point_adjusted_equalizations` may continue to omit `plan_types`: the server supplies both currently supported values, `MONTHLY,UPFRONT`, and preserves that scope on continuation pages. Explicit filters keep their existing meaning.

Enable the new domain explicitly with `--workers assets` or add `assets` to your existing comma-separated selection. The complete catalog becomes 514 tools and 36 worker filters. `--read-only` blocks `assets_apply_change` and the review-addition alias, including direct calls to hidden tools.

## Discover, prepare, apply, inspect

1. Call `assets_get_library` with `app_id` and `assets_get_reference_data`. The catalog describes enabled features, placement groups and file specifications; do not hardcode dimensions or infer them from extensions.
2. Browse `assets_list_images` / `assets_list_videos` and inspect a resource with `assets_get_image` / `assets_get_video`. Repeat the original selectors and filters when using `next_url`.
3. Prepare an upload with `assets_prepare_change`: `app_id`, `action: upload_image` (or `upload_video`), `category`, and an absolute `file_path`. Optional target constraints validate the intended use, but do not create a placement. The preview reports the snapshot SHA-256, matching specifications and operation ID.
4. Review the preview in the MCP client. Apply it with `assets_apply_change` and **only** `preview_id`. It expires after ten minutes, cannot be reused and becomes invalid after an account switch or restart.
5. Inspect `assets_get_operation`. `processing_pending` means transfer/commit may be complete while Apple is still processing. It is not permission to recreate the upload or proof of readiness for placement/review.
6. Once processing and the assigned specification are verified, prepare `create_placement` with `asset_kind`, `asset_id`, `target_type`, `target_id`, `placement_type` and `placement_group`. A file can have multiple placements.

Other typed actions are `update_reference_name`, `update_video_poster`, `replace_placement`, `delete_placement`, `reorder_placements`, `archive_asset`, `unarchive_asset`, `delete_asset`, and `add_review_item`. Unsupported combinations are rejected. Arbitrary HTTP methods, headers and destination URLs cannot be supplied.

Supported localization types are `appStoreVersionLocalization`, `appCustomProductPageLocalization`, `appStoreVersionExperimentTreatmentLocalization`, and `appEventLocalization`. Ordering excludes event placements. Mutation preflight requires verified ownership, a known state, dynamic category/spec/group/platform compatibility, capacity, and an editable parent. Published-placement changes are not promised by this release.

Replacement creates and verifies a new asset separately before changing placement. Replacing a placement may first remove the old placement and create a temporary gap. The old binary remains intact. Preview explains this boundary; failed replacement returns the completed steps instead of claiming an atomic rollback.

The preview and journal retain `previousPlacement`, including the old asset identity, target, group/type and original group order. After a partial replacement or intentional placement deletion, use those values to prepare a separate restoration and then a separate reorder if needed. The server never recreates the old placement automatically.

## Recovery

Keep the operation ID returned during preparation. After a lost response, cancellation, timeout or restart, inspect it before any new mutation. Reconciliation performs reads only. Candidate IDs from a lost reservation response are diagnostic and are not automatically adopted or transferred.

For a confirmed reservation still `AWAITING_UPLOAD`, prepare the same upload action with `resume_operation_id`, matching `app_id`/`category`, and the original `file_path`. The file name, size and SHA-256 must match. The server never creates a replacement reservation for this resume. An uncertain commit cannot be resumed this way. Follow `resumed_by_operation_id` if the journal points to a successor operation.

The journal is private, atomic and account-scoped. See [SECURITY.md](../../SECURITY.md) for retention and limits. A binary rollback does not undo Apple changes. To disable new tools, omit `assets` from the selected workers; to inspect without writes use `--read-only`. Reinstall the prior stable version with `mint install zelentsov-dev/asc-mcp@v4.1.6 --force` if needed, and preserve unresolved journal records for diagnosis.

## Review and other 4.5.1 changes

Review-submission reads support image/video relationships and mixed items. Prepare `add_review_item` with the app, asset and `submission_id`; apply normally, or use `review_submissions_add_item` with exactly `submission_id`, one `app_asset_library_image_id` / `app_asset_library_video_id`, and the matching `preview_id`. Both paths consume the same one-use preview. Older review item forms are unchanged. Attachment to a submission, submission to Apple, approval, and placement are distinct states.

`app_versions_update_age_rating` accepts Korea `ALL` and `TWELVE_PLUS` alongside existing values. `subscriptions_update` supports nullable `market_settings` and `multi_seat_status`; omission preserves existing values, and creation does not accept these update-only controls. `metrics_performance_overview` reads Apple's performance overview with the dedicated media type and optional device filtering.

## Candidate acceptance

Automated contract/unit tests and controlled MCP-process checks precede Apple acceptance. The authorized live stand is Bike tracker only: new marked resources and editable drafts, no application release, commercial price/availability changes or published-placement edits. Missing capabilities remain blockers rather than moving tests to another app. Record the exact candidate commit, resource IDs, Apple read-back and ASC UI results; clean up only unequivocally created test resources.

The controlled fixture command is `python3 -B .github/workflows/scripts/assets_mcp_smoke.py --binary .build/release/asc-mcp --expected-version 4.2.0`. It generates fake credentials, uses only a loopback API fixture, checks the stdio protocol and private journal, and cleans up only its own resources. Run it after the repository's MCP reload confirmation, followed by the authorized Apple scenarios. It cannot establish Apple compatibility by itself.
